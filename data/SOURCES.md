## 2. The SOP corpus — authored, not scraped

**No agency publishes its internal SOPs.** Any honest version of this project must
author them, and pretending otherwise would be the more serious misrepresentation.

Each of the 17 SOPs is a **synthetic officer-facing procedure**. Every factual claim
in one traces to a public IRAS URL recorded in that file's `references:` frontmatter —
**30 distinct URLs**, all on `www.iras.gov.sg`.

Three structural guarantees, enforced at load time rather than by convention:

- **Every SOP carries a synthetic banner.** `src/triage/sop/loader.py` raises at
  startup if `synthetic: true` is missing. A corpus that could be mistaken for real
  agency material is the failure mode this guards against.
- **Every SOP must declare at least one reference.** An empty `references:` list is a
  hard load error.
- **Citations are checked, not assumed.** `python scripts/generate_sops.py --check`
  validates that all 148 recorded facts resolve to a declared source. It is a
  Makefile target and part of the normal build.

None of these files reflects internal IRAS material, template, or practice. They are
my reconstruction of what such a procedure would plausibly contain, written to a
frontmatter schema designed so a real agency could conform its own SOPs to it without
touching the code (`sop_design.md` S12).

### 2.1 How the reference pages were used

`scripts/fetch_reference.py` fetches the registry of public pages into `.scratch/`,
which is **gitignored** (`.gitignore` line 3). The manifest records the URL, fetch date
(2026-09-01), HTTP status and byte count for each.

The fetched HTML exists **only** so that facts written into the SOP specs can be
checked against their source during human review. It is never committed, never
redistributed, and never fed to a model.

Politeness measures: a courtesy rate-limit between requests (`--delay`, default
applied in the fetch loop), a single pass rather than a crawl, and a fixed registry of
~30 named pages rather than link-following. A browser User-Agent is set because the
IRAS site serves a JavaScript navigation shell to unknown agents and returns no
content otherwise — this is to receive the page a human would see, not to evade a
restriction.

### 2.2 Licensing position, stated plainly

IRAS Terms of Use restrict reproduction of site contents. Read literally, they also
require written permission to hyperlink to an internal page — a provision that reads
as boilerplate and is not observed in practice anywhere on the Singapore web.

**This project does not depend on resolving that question**, because it does not
reproduce site content. The operative principle is that **copyright protects
expression, not facts**. A filing deadline, a relief cap, and a penalty rate are facts
stated in or derived from legislation; they are not anyone's creative expression.

What is committed is my own prose restating those facts, with a citation to where each
came from. What is not committed is any IRAS page, in whole or in part.

**Note on figures.** Relief caps and rates in the SOPs are stated as the public pages
state them. They are a snapshot taken 2026-09-01 and will go stale — a production
version would need effective-date metadata and a re-indexing cadence, which is listed
under future improvements in the README.

## 3. Synthetic emails

3,000 emails generated by **GPT-4o** from 116 hand-authored scenario specifications.

### 3.1 Why synthetic

Real citizen correspondence to a tax authority contains NRICs, addresses, income
figures and financial distress. It cannot be obtained lawfully for a take-home
exercise, cannot be ethically used if it could, and no public corpus of Singapore
government email enquiries exists. Synthetic is the only honest option here, and the
question becomes whether it is generated well enough to support a claim.

### 3.2 What makes it defensible

**The generator never sees the label.** It receives a *situation* description
("someone received a message claiming to be from the tax authority asking them to
confirm bank details, and wants to know if it is real"). The class label is attached
afterward from the scenario file. The model cannot write toward a class name, which is
the mechanism that would otherwise plant a giveaway token in every email of a class.

**Three independent axes of variation:**

- *Content* — persona, life situation, and the guidance actually relevant to it.
- *Style* — standard English; imperfect English with typos, run-ons and all-caps;
  lightly Singlish-inflected. Register calibrated against sampled real CFPB complaints
  (read for tone; no text copied).
- *Season* — filing period, estimates, notice-of-assessment period.

Plus an edge-case slice: answerable only from held-out guidance, account-specific
phrasing, and genuine edge cases recalled from prior call-centre experience.

**Model separation.** The generator (OpenAI GPT-4o) differs from the zero-shot
classification baseline and the groundedness judge (both Groq/Qwen). No model in the
evaluation path is ever scored on text it wrote — enforced as an explicit rule in
`config/models.yaml`.

### 3.3 Leakage is tested, not assumed

`python scripts/check_leakage.py` runs seven checks over the committed corpus. All
seven pass on the current one:

0. **Balance** — class counts against the taxonomy (300 per class × 10).
1. **Vocabulary leakage** — a TF-IDF + logistic-regression probe. It should classify
   *well but not perfectly*: a near-perfect score means a giveaway token exists and the
   corpus needs regenerating. Measured accuracy sits in the expected band.
2. **System vocabulary** — no email contains the system's own terms (bucket names,
   SOP ids, class names).
3. **Length as a giveaway** — that message length alone does not carry class signal.
4. **Near-duplicates** — cosine similarity across the corpus.
5. **Boilerplate** — that generated openings and closings do not cluster by class.
6. **Flag confounding** — that a lexical flag is not standing in for a class.

Separately, **splits are grouped by `scenario_id`**, so every variant of a situation
lands in the same split and no paraphrase straddles the train/test boundary. That is
enforced in `scripts/make_splits.py` and verified by zero scenario overlap between
every pair of splits.

### 3.4 Privacy in the generated data

- **All NRICs are fake.** Checksum-valid so the detector can be tested honestly, but
  not issued to anyone. No real identifier appears, including my own.
- Addresses are constructed from real Singapore street and estate names with invented
  block and unit numbers — locating a plausible place, not a person.
- Phone numbers follow the Singapore 8-digit format; postal codes are 6-digit runs.
  None is a real subscriber line or a verified address.
- **What was planted is recorded** (`plant_pii` per email), which is what makes scrub
  recall measurable rather than asserted.

### 3.5 Privacy in the pipeline itself

Beyond the data, three properties of the system:

- **Scrubbing happens before any external call.** The classifier and the drafter both
  see placeholder text; real values never leave the machine. Rehydration is local and
  happens after the network call, in exactly one place.
- **No PII in committed results.** `eval/metrics/pii_recall.py` masks missed values at
  the point of capture (`S0433218J` → `S0*****8J`), so the module that measures
  containment cannot itself write an identifier into `eval/results/`.
- **`.env` is gitignored** and `triage.env.key_status()` reports only booleans, never
  key values.

## 4. CFPB Consumer Complaints

- **Source:** US Consumer Financial Protection Bureau complaint database, accessed via
  Hugging Face.
- **Licence:** US federal government work — public domain. The publisher redacts PII
  before release.
- **Use:** read to calibrate *register* — how members of the public actually write to
  an institution when frustrated, confused, or in financial difficulty. Sentence
  length, politeness markers, how a complaint opens.
- **Not used for:** training, evaluation, or text reuse. No CFPB text appears in this
  repository. It is American and about consumer finance, so it is a style reference
  only, never a content one.

## 6. What this data does not cover

Recorded here as well as in the README, because it bounds every number reported:

- **116 situations is the binding constraint**, not 3,000 emails. Per-class figures
  rest on ~90 test emails drawn from a handful of situations each, so a class can look
  strong because its few situations happen to be easy.
- **A synthetic ceiling.** This measures performance on a distribution GPT-4o and I
  jointly imagined. It cannot tell you a real inbox looks like this — that is the one
  thing this project cannot check about itself.
- **One agency, one tax type.** Individual income tax only. No corporate tax, GST,
  property tax, or stamp duty.
- **English only**, with Singlish inflection. No Chinese, Malay or Tamil.
- **No attachments, no threads, no forwarded chains.** Every email is a single
  standalone message, which real correspondence often is not.
- **Author-shaped distribution.** The scenario set reflects what I judged
  representative. A real inbox would be shaped by seasonality, campaigns, and
  events nobody anticipated.

The most valuable next data step is not more emails — it is **more situations**, and a
validation-only slice of real anonymised enquiries to test whether the synthetic
situation set resembles the real one.
