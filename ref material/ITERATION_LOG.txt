METHOD NOTE -- what actually worked
================================================================================
The productive loop was the same every time:

  1. Find the weakest class by F1.
  2. Break it down PER SCENARIO, not per class. Every real defect showed up as
     one scenario at 0.00 sitting beside a sibling at 1.00. A class-level
     average hides that completely.
  3. Read the actual emails the model got wrong, and the model's confidence.
     High confidence on a "wrong" answer means the label is wrong, not the model.
  4. Fix the corpus. Regenerate only the affected scenarios (--resume skips by
     email id, so this costs minutes, not hours).
  5. Re-split, retrain, re-evaluate, commit with the numbers in the message.

What never helped: reaching for a bigger model, or for an LLM. Both were
measured rather than assumed, and both lost.

One metric caution that recurred: CLASS accuracy is not the objective. 127 of
234 class errors at one point were invisible downstream -- same bucket, same
action, same SOP group. BUCKET accuracy is the number that tracks what the
citizen receives, and out_of_scope recall was the single most valuable thing
measured all session, because those errors send a citizen a substantive tax
answer when they should have been redirected to another agency.
